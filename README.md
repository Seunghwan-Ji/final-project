# 기초 다지기
- 머신러닝과 딥러닝의 정의부터 공부하였다.
  둘의 경제적인 용어 차이와 층의 구조 차이를 알게되었고, 이들은 알고리즘 종류가 크게
  '지도학습', '비지도 학습', '강화학습' 으로 나뉘며
  주로 '지도학습'의 '분류' 문제와 '회귀' 문제중 적합한 알고리즘이 사용되는 활성화 함수들을 배웠다.

  머신러닝보다 비교적 어려운 문제를 잘 해결하는 딥러닝 이론에 관심이 생겼다.
  딥러닝 이론을 코딩으로 실습하기 위해 'TensorFlow' 도구를 사용하였다.
  처음엔 표 형태의 데이터를 기준으로 여러 신경망을 결합하여 입력층, 은닉층, 출력층을 이루는
  다중 인공신경망 형태의 층의 구조를 설계하고 원리를 이해하게되었다.
  
  다음으로 이미지 형태의 데이터로는 먼저 입력 이미지의 차원 개념부터 배웠다.
  이미지의 특정 패턴으로 특징맵을 구성해 각 층에서 학습시킨다음
  표 형태의 데이터로 변환하는 층을 만들고 이어서 분류하는 학습 과정을 알게되었다.

  결론적으로 표 형태의 데이터를 학습하는 기본 딥러닝 모델은 가중치를 학습해서 최적의 특징을 만들고,
  이미지 형태의 데이터를 학습하는 CNN(Convolutional Neural Network) 구조 딥러닝 모델은
  패턴(filter)을 학습해서 최적의 특징맵을 만든다는것을 이해했다.

- 층의 구조가 이미 정의되있고 사전 학습이 되어있는 'yolo' 모델에 대해서도 공부해봤다.
  이 모델도 CNN 구조의 딥러닝 모델이며, 기본적으로 객체 탐지 모델이다.
  객체 클래스를 정의하여 이미지상에서 객체를 탐지하는 기술이 인상 깊었다.
  그래서 yolo 모델로 프로젝트를 진행하기로 결정하였다.
  
  사전 학습된 모델이라 바로 예측이 가능했지만 특정 데이터셋에 맞게 조정하여 탐지하도록 하려면
  이 모델을 파인튜닝(사전학습 모델 추가훈련) 해야했다.
  'roboflow' 라는 사이트에 업로드된 임의의 메타 데이터로 파인튜닝 실습을 해보았다.
  'yaml' 이라는 형식의 파일에서 객체 클래스를 정의하고
  모든 이미지마다 객체의 위치와 클래스번호가 라벨링된 파일이 갖춰졌다면
  파인튜닝을 진행할 수 있었다. 'roboflow' 사이트의 메타 데이터는 이런것들이 갖춰져있기때문에
  바로 파인튜닝을 하고 예측을 수행한다음 결과를 확인해보았다.

- 로컬 환경에서 모델을 학습 시키는 시간을 줄이기 위해 CPU 대신 GPU 연산을 하게하는 방법을 찾아보았다.
  우리는 NVIDIA GPU를 사용중이이므로 NVIDIA가 제공하는 개발자 도구인 GPU 가속을 활용한 고성능 연산을
  가능하게 하는 'CUDA', 와 'cuDNN' 을 설치하였다.
  
  그리고 우리는 딥러닝 프레임워크중 하나인 'PyTorch' 를 기반으로한 YOLO 모델을 사용중이기 때문에
  'PyTorch' 를 설치하였다. 'PyTorch' 는 GPU를 활용한 연산을 지원한다. 'PyTorch' 에서
  'CUDA' 를 통해 GPU에서 연산을 수행하며, 'cuDNN' 을 통해 딥러닝 연산의 속도를 최적화한다.

  GPU는 병렬 처리에 최적화된 구조로 설계되어 대량의 데이터와 복잡한 수치 연산을 효율적으로 처리할 수 있으며,
  CPU 보다 훨씬 많은 코어 수로 동시에 많은 연산을 수행할 수 있다.
  딥러닝 연산은 동일한 작업을 대량의 데이터에 적용하는 형태인데 CPU의 병렬 처리능력은 한계가 있다.
  이러한 연산을 최적화하여 병렬로 수행할 수 있다는 점이 GPU를 사용하는 가장 큰 이유인거 같다.

# 프로젝트 시작: 데이터 수집, 전처리, 모델링
- 이제 본격적으로 프로젝트를 시작하였고, 'roboflow' 사이트에서 데이터를 수집했다.
  두개의 데이터셋을 수집했는데 하나는 라벨링이 되있었고 다른 하나는 안되어 있었다.
  라벨링이 안되어 있는 데이터는 train 이미지만 존재했었고 test, valid 이미지들은 존재하지 않았다.
  그래서 이미지 개수를 train : test = 7 : 3 으로 분할한 다음
  train : valid = 7 : 3 으로 분리하고, 마무리로 train, valid, test 각각
  labels 폴더를 만들고 그 안에 직접 라벨링 해준 텍스트파일을 넣었다.
  이후 이 두 개의 데이터셋을 합치기로 했다. 중복되는 클래스를 하나의 
  클래스 번호로 통일하고 중복되지 않는 클래스는 한 데이터의
  마지막 클래스 번호 다음 순서로 매겨주는 식으로 yaml 파일을 만들어주었다.
  마지막으로 파인튜닝을 마치고 테스트 이미지들을 예측해서 결과를 확인하였다.

# 웹캠 실시간 객체(식재료) 탐지 기능
- 이제는 정적인 이미지 말고도, 웹캠을 연결했을때 화면상에 실시간으로 포착되는
  객체를 탐지하는 과정을 연구해보았다. 수행방법으로는 이미지 처리 기술 라이브러리인 'opencv' 를 활용하였다.
  먼저 웹캠 화면 영상을 프레임 이미지 단위로 나누고, 그 프레임 이미지 내에서 모델이 객체를 탐지한다.
  탐지된 객체의 정보(바운딩된 박스 좌표, 라벨, 신뢰도)를 객체 위치에 표시하여 편집된 프레임 이미지를 반환하는 과정을 반복했다.
  매 프레임마다 예측 결과를 시각적으로 확인할 수 있었다.

- 웹캠 실시간 객체 탐지 테스트를 해보았을때 모델이 올바르게 예측하는 객체도 있었고 
  틀리게 예측하는 객체도 있었다. 그래서 모델의 성능을 높일 방법을 생각해보았고,
  해결책으로 더 다양한 데이터가 훈련된 모델을 만들면 되지 않을까 생각했다.

# 모델 성능 개선
- 그러나 더 많은 데이터셋을 구하기는 했지만 이 데이터셋들을 합치려면
  중복되는 클래스를 통합하고 yaml 파일을 재정의 해야하는 번거로움이 있었다.
  문득 생각난것이 그냥 각 데이터셋마다 파인튜닝된 모델을 만들고 그 모델들을 
  합칠 방법이 없는지 궁금해서 정보를 찾아봤더니 유명한 방법중 하나인 앙상블 기법이란 것을 알게되었다.

- 다시 처음으로 돌아가 각 데이터셋마다 파인튜닝된 모델을 만들기전에 모든 데이터셋의 라벨들을 모아
  종합하여 한글 번역 사전을 만들었고, 각 데이터셋의 yaml 파일안에 영어 라벨들을 한글 번역 사전에
  맵핑하여 한글 라벨로 수정해주었다. 그리고 이미지 사이즈가 같은 데이터셋들만 남겨두었고,
  입력 이미지 사이즈를 실제 이미지 사이즈로 통일해주었다. 입력 이미지 사이즈를 통일한 이유는
  각 모델마다 동일한 해상도에서 예측이 수행되어야 예측들을 비교하기 편하기 때문이다.
  
  파인튜닝은 사전학습된 yolo 모델중 'yolov10s' 모델로 진행하였다. 이 모델을 선택한 이유는
  우리가 사용중인 gpu 스펙을 기준으로 gpu 메모리 소모량이 적당하고, 학습속도가 최대한 오래걸리지 않는 선에서
  이 모델이 우리 로컬 환경에 쓰이기 적합하다고 판단했다.
  이제 파인튜닝을 다 마친 모델들을 모아서 로드해주고 앙상블 기법중 'Non-Maximum Suppression' 알고리즘 방식을 사용해보았다.

  ## 기술, 알고리즘
    ### NMS(Non-Maximum Suppression) 알고리즘 방식
    - 동일 객체에 대해 여러개의 바운딩 박스가 탐지되었을 때 각 박스의 신뢰도(confidence)를 기준으로
      가장 신뢰도가 높은 박스를 선택하고, 중복되는 박스는 제거하는 방식이다.

      먼저 각 바운딩 박스의 신뢰도를 기준으로 내림차순으로 정렬한다.
      가장 높은 신뢰도를 가진 박스를 선택하고, 이 박스와 겹치는 다른 박스들을 계산한다.
      겹치는 박스의 IoU(Intersection over Union: 두 박스 영역의 교집합을 합집합으로 나눈값 즉, 겹침 정도의 비율)가
      특정 임계값(예: 0.6) 이상인 경우, 그 박스는 삭제한다.
      이 과정을 반복하여 남아있는 박스 중에서 최종 바운딩 박스를 결정한다.

    - 그러나 NMS 방식에서 문제가 있었다
      여러개의 모델중 과적합 훈련된 모델이 일부 있을경우 틀린 예측을 하는 반면
      신뢰도도 매우 높게 나와서 과적합 모델이 바운딩한 박스와 신뢰도, 라벨이 선택되어버린다.
      나머지 다수 모델들의 신뢰도는 일부 소수의 과적합 모델의 신뢰도보다
      살짝 낮지만 객체는 올바르게 예측하였다.

      그래서 앙상블 기법중 또다른 알고리즘인 다수결 알고리즘 방식이란 것도 사용해보았다.

    ### 다수결 알고리즘 방식
    - 여러 모델의 탐지 결과에서 가장 많이 나온 라벨을 결정하기 위한 방식이다.

      먼저 모든 박스를 서로 한 쌍씩, 겹침 정도의 비율인 Iou를 계산하고 Iou를 1에서 뺀 값이
      특정 임계값보다 작으면 많이 겹쳤다고 판단한다.(Iou는 비율을 나타내기 때문에
      0~1 사이의 값이므로 클수록 1에서 뺀 값이 작아진다.)
      그런데 Iou값을 굳이 1에서 빼지 않아도 되며, 빼지 않는다면 Iou가 특정 임계값보다 크면 많이 겹친다고 판단하면된다.
      예를들어
      "Iou를 1에서 뺀 값이 0.4 미만일 경우 많이 겹친다고 판단한다"
      "Iou 값이 0.6 초과일 경우 많이 겹친다고 판단한다"
      두 문장은 서로 같은 의미이다. 일반적으로 거리나 유사도를 나타내는 값은 클수록 비슷하지 않음을 나타내는 것이 보편적이라고 한다. IoU는 겹침 정도를 나타내는 값이므로, 이를 1에서 빼면 비슷하지 않거나 멀리 떨어져 있는 정도를 표현할 수 있다.
      
      다음으로 서로 많이 겹쳐진 박스들끼리 그룹화 한다.

    - 여기서 특정 임계값를 기준으로 겹칩의 정도를 판단하고, 서로 많이 겹쳐진 박스들끼리 그룹화 하는 이유가 뭘까?

      우선 겹쳐진 박스들끼리 그룹화하는 이유부터 설명하겠다.
      어느 하나의 특정 객체를 포착한 모델이 여러개 있다고 가정하자, 그러면 그 객체는 바운딩된 박스를 여러개 갖고있을 것이다.
      예측한 라벨과 신뢰도 또한 여러개이며, 이것들이 만장일치라고 확신할 수 없다.
      그렇기 때문에 우선 이 하나의 객체를 기준으로 바운딩된 박스들을 그룹으로 묶고난 이후에
      이 객체에 적합한 박스 좌표, 신뢰도, 라벨을 결정할 필요가 있다.

      다음으로 그룹화 이전에 특정 임계값 기준으로 겹침의 정도를 판단해야하는 이유는
      예를들어 서로 다른 객체가 비교적 가까이 붙어있다고 가정한다면, 서로 다른 객체에 대해서 바운딩된 박스가 겹칠 수 있다.
      그룹화는 겹쳐진 박스들끼리 그룹화하되 한 객체에 대해 바운딩된 박스들끼리만 그룹이 이루어져야한다.
      객체에 대한 정보를 결정하기 위해서는 한 그룹에 다른 객체에 대해 바운딩된 박스가 포함되지 않아야되기 때문이다.
      상식적으로 한 객체에 바운딩된 박스들은 웬만하면 차이가 거의 없을정도로 많이 겹쳤을 것이다.
      그렇기 때문에 특정 임계값 기준으로 많이 겹쳤다고 판단하는 과정을 거치고난 후 그룹화를 진행한다면
      서로 다른 객체가 가까이 붙어있다고 해도 한 그룹에 다른 객체에 대해 바운딩된 박스가 포함되지 않을것이다.

    - 이제 각 객체의 박스 좌표, 신뢰도, 라벨을 결정한 방법이다.
      박스 좌표: 각 그룹에서 박스들의 좌표의 평균(박스의 좌표는 우상단과 좌상단 두 꼭짓점의 좌표를 말한다.)
      신뢰도: 각 그룹에서 박스들의 신뢰도의 평균
      라벨: 각 그룹에서 라벨중 빈도수가 가장 높은것

      마지막으로 프레임 이미지에 결정한 박스 좌표 위치에 사각형을 그리고, 라벨과 신뢰도를 텍스트로 표시한다.

    - 그러나 다수결 방식에도 일부 과적합 모델들이 말썽이었다.
      일부 과적합 모델들을 제외시켰고, 조건을 더 추가하였다.
      그리고 특정 조건에선 NMS 방식을 사용하였다.

      다음은 최종 예측을 수행하는 과정이다.

  ## 알고리즘 통합, 최종 기술
    ### 각 모델들이 감지한 객체의 수
    **ex) detection_counts**:

    **[1, 2, 2, 0, 1, 1, 0, 1]**

    - 총 8개의 객체 감지, 바운딩된 박스의 수: 8개

    - 각 요소의 수는 모델의 수와 같고, 각 인덱스는 모델의 번호이며,
      각 요소가 의미하는것은 모델이 감지한 객체의 수이다.

    ### 겹치는 박스끼리 박스의 번호로 그룹화(서로 겹치는 정도가 특정 임계값보다 커야 그룹을 이룸)
    **groups**:

    **[[0], [1], [2, 4, 7], [3, 6], [5]]**

    - 바운딩된 0번부터 7번까지의 박스들중 3개가 서로 많이 겹쳐 그룹을 이루고, 또 다른 2개가 서로 많이 겹쳐 그룹을 이룬다.
      나머지는 겹치는게 없는 단일 박스이다.

    ### 박스가 적어도 3개이상 겹치는 그룹만 통과
    **[[2, 4, 7]]**

    - 라벨 빈도수를 조사하여 다수결을 적용하기 위해선 박스가 최소 3개이상 겹치는 그룹이어야한다.
      만약 3개이상 겹치는 그룹이 없다면 박스, 신뢰도, 라벨 모두 빈 리스트를 반환하고
      화면에 객체의 정보를 표시하지 않는다.

    ### 그룹에서 각 박스의 라벨을 추출하고, 각 라벨의 빈도수중 최빈값에 해당하는 라벨을 선택
    **ex) ['계란', '계란', '감자']**

    - 최종 라벨은 **계란** 으로 결정된다.

    ### 그러나 만약 다음과 같이 최빈값에 해당하는 라벨이 여러개인 경우라면
    **ex) ['계란', '계란', '감자', '감자', '양파']**

    - 이 경우엔 최빈값에 해당하는 라벨인 '계란', '감자'에 해당하는 박스들끼리 NMS 방식을 적용하여
      신뢰도가 더 높은 박스의 라벨을 선택한다.

    ### 이번엔 다음과 같이 빈도수가 모두 1인 라벨들로 구성되어 있다면
    **ex) ['계란', '감자', '양파']**

    - 모두 NMS 방식을 적용해 신뢰도가 가장 높은 박스의 정보를 반환한다.

    - 즉, 최빈값이 1보다 큰 경우는 공통 최빈값을 갖는 박스들끼리만, 최빈값이 1인 경우는 모든 박스들에 NMS를 적용한다.

    ### 개선사항
    - 다음으로 수행속도 측면에서 개선한 부분이 있다.
      만약 모델 수가 많아지면 각 모델이 순차적으로 예측을 수행하므로 시간이 오래 걸릴것이다.
      또한 웹캠 화면의 실시간 프레임 이미지를 주기적으로 시각화 해야하기에 수행시간이 지연되면
      보여지는 화면 프레임 또한 지연되어 영상이 끊기는것을 체감할 것이다.
      그렇기에 최소한 개별 모델 예측 수행속도는 빨리 이루어져야 한다.
      그래서 모든 모델이 동시에 예측을 수행하길 원했고, 각 모델에 대해 스레드를 생성해주었다.
      개별 스레드에서 각자 예측을 동시에 수행하게 되었으며, 예측이 끝난 스레드는 리스트에 결과를 기록하게했다.
      모델마다 예측 수행시간은 각기 다르므로 모든 스레드가 리스트에 결과를 기록하고 종료될 때까지 기다린다.

      이제 모든 스레드가 종료되면 모든 모델의 예측 결과가 기록된 리스트를 가지고 앙상블 기법을 시작하여 최종 예측을 결정한다.

# 탐지된 식재료들로 조리하기 적합한 레시피 추천 기능
- 이제 최종 예측된 정보(탐지된 식재료들)를 가지고 레시피를 추천하는 단계를 구성해야한다.
  우선 웹캠 화면에서 매 프레임 이미지마다 최종 예측된 정보를 집합에 저장시켰고(중복된 라벨이 저장되지않게 집합을 사용하였다.)
  이 집합을 '탐지된 식재료 집합' 이라고 부르기로 했다.

  레시피 데이터는 'KADX(농식품 빅데이터 거래소)' 사이트에서 '만개의 레시피(한식 레시피 사이트)' 사이트를 분석한
  한식 레시피 데이터 csv 파일을 다운받았다. 이후 'Pandas' 라이브러리로 데이터 프레임으로 변환한 다음 데이터들을 확인해보니
  약 18.5만개의 행이 있음을 확인했다.

  이 데이터 프레임에서 우리가 주로 전처리하여 사용한 열들은 다음과 같다.

  '요리명', '재료리스트', '조회수', '추천수', '스크랩수',
  '요리타입', '음식분위기', '재료타입', '음식타입', '몇인분',
  '요리난이도', '요리시간', '레시피일련번호'

  여기서 주로 '재료리스트' 열에서 불린참조 하게된다.
  기본적으로 '탐지된 식재료 집합' 에서 적어도 하나 이상의 재료가 '재료리스트' 열에 포함하되 많이 포함된 순으로 행을 추출할건지,
  모든 재료가 '재료리스트' 열에 포함되는 행을 추출할건지를 두 가지 선택지로 사용자에게 제시한다.
  
  만약 선택한 선택지가 '재료가 많이 포함된순' 이라면, 데이터 프레임에 '포함된 재료 개수' 열과
  '포함된 재료' 열을 새로 추가한다. 모든 행에 대해서 각 열에는 '탐지된 식재료 집합' 을 불린참조해서
  '재료리스트' 열에 포함된 재료 개수와 재료들을 담는다.
  이후 '포함된 재료 개수' 열을 기준으로 내림차순 정렬된 행들을 보여준다.

  추가적으로 각 선택지의 결과에서 사용자는 '추천순', '조회순', '스크랩순' 중 하나를 추가로 선택해 정렬기준을 설정할 수 있게 한다.
  각 정렬기준은 '추천수', '조회수', '스크랩수' 열을 내림차순 정렬하여 보여준다. 이 열들은 숫자로 보이는 데이터 같았지만,
  오브젝트 타입이 포함되어 있었기에 전처리 작업에서 데이터 타입을 정수로 변환하는 과정을 추가하였다.

- 마지막으로, 추출된 레시피 데이터 프레임에서 사용자가 행을 선택할 수 있게 하고,
  추가적으로 해당 레시피에 대한 상세안내를 시각적으로 보여주고 싶었다.

# 레시피를 선택했을때 상세안내를 시각적으로 보여주는 기능
- 우선 이 레시피 데이터는 공식적으로 '만개의 레시피' 사이트에서 분석했기 때문에
  해당 사이트에서 스크래핑 기술을 사용했다.

  먼저 요리명을 검색한 결과 페이지 URL 주소가 필요하다.
  그래서 사이트 주소와 사용자가 선택한 '요리명' 열의 문자열을 결합한 URL 주소를 정의한다음,
  'requests' 라이브러리로 URL 주소에 HTTP GET 요청을 보낸다.
  이후 응답 데이터로 받은 HTML 페이지 내용을 변수에 저장하고 그 변수를 'BeautifulSoup' 라이브러리를
  사용하여 HTML 데이터를 파싱한다. '만개의 레시피' 사이트는 요리명 검색결과를 한 페이지에 40개씩 보여준다.
  그리고 40개의 결과중에는 요리 동영상이 있는것도 있고 없는것도 있다.
  우리는 동영상이 있는 레시피를 안내하고 싶었기 때문에 다음과 같이 진행하였다.

  각 검색 결과의 태그는 패턴은 같고 숫자만 다르게 대입된 동적 태그이기 때문에
  첫번째 결과부터 40번째 결과까지 반복문을 통해 순회한다.
  웬만하면 1페이지 내에 동영상이 포함된 결과가 있기도 하고, 순회가 길어지면
  사용자가 체감해야하는 로드 시간도 길어지기 때문에 1페이지 내에서 쇼부보기로 했다.
  만약 동영상 관련 태그가 포함된 결과를 찾으면 중지하고, 40번째 결과까지 순회가 끝나도 찾지못하면
  그냥 첫번째 결과를 선택한다. 이 사이트의 검색결과는 기본적으로 추천순으로 나열되어있기 때문에
  동영상 관련 태그를 찾지 못하면 추천이 가장 많은 첫번째 결과를 선택하기로 했다.
  순회가 끝나면 최종적으로 선택된 결과를 새 URL 주소로 업데이트 한다.

  이제 이 새 URL 주소에 다시 GET 요청을 보내고 HTML 데이터를 받아서 파싱한다.
  이 주소에는 다음과 같은 정보들이 있다.

  '요리된 사진', '재료 구성', '요리 영상', '조리 순서/이미지', '팁/주의사항'

  각 정보에 해당하는 태그에서 이미지, 텍스트, 삽입된 유튜브 영상 URL 등을 성공적으로 잘 추출하였다.
  특히나 '조리 순서' 부분은 각 순서마다 메인설명과 부연설명이 나뉘어져 있는데 HTML 태그에서는
  한 태그로 묶여있었다. 이를 그냥 추출하면 두 문장이 분리되지않고 이어져서 보이기 때문에
  각 조리 순서 태그마다 메인설명 부분과 부연설명 부분을 split 한다음, 다시 줄바꿈 문자로 연결해
  최종적으로 두 문장이 분리되어 보이도록 하는 디테일을 신경썼다.

- 마지막으로 지금까지 구성한 웹캠 실시간 식재료 탐지 기능, 탐지된 식재료들로 조리하기 적합한 레시피 추천 기능,
  레시피를 선택했을때 상세안내를 시각적으로 보여주는 기능 등을 웹 사이트에 적용하는 단계를 진행했다.

# 웹 사이트에 적용
- 웹 사이트는 'Streamlit' 라이브러리를 사용하였다.
  이 도구는 데이터 과학 및 머신러닝 모델 결과를 시각적으로 표현하는 데 최적화되어 있으며,
  파이썬 코드만으로 인터랙티브한 웹 애플리케이션과 대시보드를 쉽게 만들 수 있는 장점이 있다.

  전체적인 페이지의 화면 구성은 왼쪽에는 사이드 메뉴를 표시하고 오른쪽에는 메뉴에 대한 페이지를 로드하기로 했다.
  우선 사이드바 메뉴를 구성한 요소들은 다음과 같다.

  '메인', '카메라 식재료 인식', '식재료 직접 입력',
  '무작위 요리 추천', '관심 요리 목록', '요리 검색 기록'

- '메인' 메뉴는 메인화면이며 배경 이미지, 로고 이미지, 짤막한 설명 등을 표시했다.
  
- '카메라 식재료 인식' 메뉴는 사용자 기기의 연결된 카메라 화면을 페이지에 표시해주고,
  우리의 '웹캠 실시간 식재료 탐지 기능' 이 실행된다. 물론 탐지된 식재료도 실시간으로 페이지에 표시되게 했다.
  이후 사용자가 '재료 인식 종료 및 수정' 버튼을 누르면 카메라가 종료되고 탐지된 식재료 목록을 볼 수 있는 페이지로 넘어간다.
  여기서 사용자는 잘못 인식된 식재료 라벨을 수정하거나 새로운 식재료를 추가할 수 있게 했다.
  이후 '다음' 버튼을 누르면 우리의 '탐지된 식재료들로 조리하기 적합한 레시피 추천 기능' 이 작동한다.
  기본적으로 두 선택지인 '재료가 많이 포함된 순', '모든 재료를 포함' 을 사용자가 체크박스로 선택할 수 있게 했다.
  그 다음 정렬 기준인 '추천순', '조회순', '스크랩순' 을 버튼으로 선택할 수 있게 했다.
  모든 선택이 완료되면 조건을 성립하는 모든 레시피 목록을 표 형태로 보여준다.
  여기서 사용자는 각 행의 요리명을 선택할 수 있고, 클릭하면 해당 요리의 '레시피 상세안내 보기' 버튼이 생긴다.
  이 버튼을 클릭하면 우리의 '레시피의 상세안내를 시각적으로 보여주는 기능' 이 작동하고
  해당 요리명에 대한 스크래핑이 완료되면 시각적인 상세정보 페이지가 로드된다.
  이 페이지에선 해당 레시피를 '관심 요리 목록 메뉴에 추가하기' 버튼을 눌러
  '관심 요리 목록' 메뉴에 저장할 수 있게 하였다.

- '식재료 직접 입력' 메뉴는 '카메라 식재료 인식' 메뉴에서 '웹캠 실시간 식재료 탐지 기능' 만 빠지고,
  사용자가 직접 식재료를 입력하는 메뉴이다.

- '무작위 요리 추천' 메뉴는 레시피 데이터 프레임에서 랜덤으로 행 하나를 추출해 레시피와 상세안내를 보여주는 메뉴이다.

- '관심 요리 목록' 메뉴는 레시피 상세안내 페이지에서 '관심 요리 목록 메뉴에 추가하기' 버튼을
  누른 레시피들의 목록을 도감 형태로 보여준다. '레시피 보기' 버튼과 '삭제' 버튼이 있다.

- '요리 검색 기록' 메뉴는 '레시피 상세안내 보기' 버튼을 누른 레시피들이 이 메뉴에 기록된다.
  '관심 요리 목록' 메뉴와 똑같이 도감 형태로 보이게 했다.

- 다음은 웹 사이트에 대해 개선한점들이다.
  
  모든 버튼과 텍스트에 이미지를 추가하거나 css 스타일링을 적용해서 보기좋게 하였다.
  코드의 가독성 측면에서 페이지마다 따로 스크립트 파일을 작성하여 개별 페이지를 관리하기 쉽도록 하였다.
  현재 페이지에서 이전 페이지의 기록을 수정할 수 있게 각 페이지마다 '뒤로가기' 버튼을 추가 하였다.

- 마지막으로 웹 사이트를 개발하면서 느낀점은 생각보다 단순하지 않았고 무엇보다 세션 상태 관리가
  매우 중요했다. 현재 세션 상태에 따라서 보여지는 페이지의 구성이 달라지기 때문이다.
  또 버튼의 클릭 이벤트마다 세션 상태를 어떻게 업데이트 하냐에 따라서도 페이지의 구성이 달라진다.
  UI나 페이지가 많아질 수록 세션 상태에 저장되는 변수들도 많아졌으며, 이들을 페이지 상황에 맞게 값을
  수정해야 했기에 코딩 난이도가 점점 올라갔다.
  또 특정 페이지에서는 버튼의 클릭 이벤트가 발생하면 페이지 내의 모든 UI를 재구성 해야한다.
  이때는 앱 스크립트 파일을 처음부터 다시 읽게하고, 유지할 세션 상태 변수를 제외한 모든 세션 상태를 초기화 해야하며,
  이전에 작업중이었던 특정 페이지로 다시 가기 위해선 초기화 하기 전까지의 코드 흐름을 파악하는게 중요했다.
  이점을 혼동하지 않도록 각 메뉴마다 연관된 페이지들을 따로 모듈 파일로 만들었다.
  메인 모듈에서 각 메뉴와 연관된 첫 페이지 모듈을 임포트하고, 페이지 모듈에서 다음 페이지 모듈을 임포트 하는식으로
  일관성을 유지했다.

# 추후 개선할점 또는 추가할 기능
- 사용자가 '관심 요리 목록' 에 추가한 각 레시피에 대해서 '비슷한 레시피 추천 받기' 기능을 추가할 것이다.
  예를들어 재료 타입 또는 재료 구성이 비슷하거나, 이름이 비슷한 요리를 추천해볼 수 있겠다.
  수행방법은 선택한 관심 요리의 레시피 일련번호로 행을 찾고, '재료리스트', '재료타입', '요리명' 등
  특징이 될만한 열들을 다른 행들의 열들과 유사도를 계산해서 적합한 행들을 추출하여 보여주면 될거같다.
